# Implementation Plan: Extend simple-adp’s Centralized Suite to Supervised Tasks

## Summary

Extend the existing simple-adp runner so it can execute the current classification and regression benchmarks plus supervised time-series forecasting, per-step sequence labeling, event detection, grouped ranking/recommendation, and tabular anomaly classification. Use the repository’s existing 14 ADP configurations, faithful and corrected generic-search profiles where applicable, and 50 vanilla MLP architectures for every supported task.

Keep the network family fully connected feedforward MLPs. Represent time-series inputs as fixed-size windows, recommendation inputs as user–item feature rows, and grouped ranking inputs as candidate rows with group metadata. Do not add novelty detection or specialized network architectures.

The existing OpenML pools remain enabled: 72 CC18 classification tasks, 36 TabZilla classification tasks, and 35 CTR23 regression tasks—143 suite-task entries, not necessarily 143 unique underlying datasets. The current provider fetches those tasks at run time.

Record these dynamic OpenML suite pools separately from downloadable artifact entries in the catalog: CC18 study suite 99, TabZilla suite 379, and CTR23 suite 353. At plan creation, resolve and persist the exact ordered task IDs and each task's dataset ID, source metadata, and split hash; the counts above are expected counts and a mismatch must fail planning rather than silently changing the benchmark.

## Stepwise implementation

1. Freeze and document the dataset catalog.
   - Add a versioned catalog manifest. Each entry records provider and task IDs, source URL, artifact/version, checksum, feature/label schema, license and attribution, access-policy result, and split protocol. Do not commit dataset payloads; cache downloads outside Git.
   - Keep CC18, TabZilla, and CTR23 unchanged. Add eligible datasets from the Monash Forecasting Repository and UCI Electricity Load Diagrams for forecasting; UCI HAPT for per-step activity labels; MIT-BIH, MIT-BIH Long-Term ECG, and NAB for event labels; the public labeled tabular datasets in ODDS for supervised anomaly detection; and MovieLens 100K and 1M for rating and per-user ranking.
   - Apply the agreed eligibility rule to every artifact: exclude anything requiring an account, approval, credentials, or click-through data agreement. Record public-use restrictions and attributions; keep use within the terms published for the data.
   - Exclude LETOR/MSLR search-ranking data under that rule. Benchmark grouped ranking as per-user item ranking from MovieLens. Do not present rating-derived preference labels as click-through data.
2. Add task data and context contracts.
   - Extend the current TabularTaskData payload with aligned row context and task metadata. Context may carry series/entity IDs, timestamps, ranking group/user IDs, and event labels; it must be serializable into the run manifest or reproducibly derivable from the dataset catalog.
   - Add a prepared-example representation containing fixed-size X, y, optional context, feature order, and provenance. Dataset providers are responsible for converting source data into examples; model adapters receive prepared examples and do not implement dataset-specific transformations.
   - Extend TaskAdapter methods additively with optional context: target fitting/encoding, loss, minimized validation score, prediction conversion, and evaluation metrics. Keep existing classification/regression behavior intact when context is absent.
   - Extend estimator fitting with optional training and validation context. Pass context through the stage trainer and validation path. Add a group-preserving sampler for ranking minibatches so a query/user group is never split; in full-batch mode, use the entire training partition.
3. Implement task preparation, targets, and metrics.
   - Forecasting: Build lag-window rows with fixed lookback 128 and strides 1 for series shorter than 10,000 observations, otherwise 24. Predict one-step and horizons 7 and 28 where the dataset frequency supports them. Use source-provided official horizons/splits when available; otherwise split each series chronologically 70% train, 10% validation, 20% test. Training targets must end before the training boundary; validation/test inputs may use already observed history, but no future target may enter features. Fit scaling on training windows only. Use MSE for training/search and report MAE/RMSE.
   - Per-step sequence labeling: Use HAPT raw six-channel sensor data in non-overlapping 128-sample windows. Predict one activity label per sample with flattened per-window logits; ignore uncovered tail samples. Keep subjects disjoint, use the source train/test subject split, and take validation subjects only from the source training subjects. Fit scaling on training windows only. Use cross-entropy and report accuracy, macro-F1, and per-step event boundaries where available.
   - Event detection: Prepare MIT-BIH beat-centered windows of 360 samples at 360 Hz and apply the documented five-class AAMI grouping (N/S/V/F/Q). Use the first recorded signal channel, centered with 180 samples before the annotation and 180 samples beginning at the center; discard annotations whose complete window is out of range. For LTDB, call WFDB `resample_sig` to 360 Hz and round each annotation's scaled sample position to the nearest integer. Use record/patient-level splits, never beat-random splits, keeping paired records 201/202 in the same partition. For NAB, generate 128-value windows at stride 24 and label positive on inclusive overlap with a published interval; split by file so a time-series file cannot cross partitions. Threshold predicted window labels at the adapter's class decision, merge consecutive positive windows per file into alarms, process alarms in `(file_id, window_index)` order, and match each alarm to the smallest still-unmatched overlapping event ID. Count each alarm and each event at most once; an alarm overlapping no unmatched event is a false positive and an unmatched event is a false negative. Report these event-level precision/recall/F1 values separately from window-level classification metrics.
   - Ranking and recommendation: Treat each user as a ranking group. Encode user and item IDs as categorical one-hot features learned from training rows; unseen categories map to the preprocessor’s unknown representation. Split each user’s interactions chronologically 80/10/10. Predict ratings with MSE and report RMSE/MAE. For ranking, treat ratings ≥4 as relevant and ratings ≤3 as non-relevant; train with pairwise logistic loss using one deterministically sampled negative per positive and evaluate only against held-out rated candidates with NDCG@5/10 and Recall@5/10. Expose binary preference prediction with the same threshold as a separate classification task, clearly labeled as rating-derived preference rather than click prediction.
   - Supervised anomaly classification: Use the labeled normal/anomaly targets supplied by each eligible ODDS dataset. Make a seeded stratified 60/20/20 split using a local NumPy `default_rng(seed)` separately to shuffle each sorted class index. For each class, allocate `floor(0.6*n)`, `floor(0.2*n)`, and the remainder to train/validation/test; reject if any class is absent from a partition. Compute `pos_weight = n_train_negative / n_train_positive` from training labels only; train with `binary_cross_entropy_with_logits`. Select the validation threshold by maximizing binary F1 over sorted unique validation probabilities plus `{0, 0.5, 1}`; on equal F1 choose the larger threshold. Freeze it before test evaluation. Report PR-AUC (average precision with tied scores grouped), ROC-AUC (average ranks for tied scores), precision, recall, and F1.
   - For every task, use its differentiable validation loss for architecture selection: MSE for numeric targets, cross-entropy for multiclass tasks, weighted BCE for anomaly/preference classification, and pairwise validation loss for ranking. Report benchmark metrics separately; do not treat them as interchangeable or aggregate them into one cross-task accuracy.
4. Connect task providers and metrics to the existing runner.
   - Register each provider and suite explicitly through the existing DatasetRegistry. Providers list stable task references, load or prepare data, and return their split definitions. Unknown provider/task IDs fail clearly; no automatic task discovery silently changes a run.
   - Update the existing SimpleADPModelAdapter to select a TaskAdapter from the task payload, pass row context through fit/validation, and emit task-family and metric metadata. Remove the runner’s classification/regression-only branches from result construction and screening by using adapter-provided metrics and a declared primary validation metric.
   - Preserve route generation exactly: the 14 canonical ADP IDs; both generic profiles for generic-search configurations; existing configured initial-width/depth sweeps; MLP-Fixed over the 50 uniform architectures formed by depths 1–5 and widths 1, 2, 4, 8, 16, 32, 64, 128, 256, and 512; and each individual vanilla architecture route.
   - Keep architecture-search behavior, optimizer profiles, compatibility quirks, and checkpoints unchanged. Only task output dimensions, target handling, validation score, and task-specific evaluation are adapted.
   - Extend result JSONL records and reports with task family, task variant, split protocol, metric names/directions, and provenance. Rank models only within the same dataset/task/metric group. Preserve all current pressure-aware scheduling, restart, telemetry, retry, and report behavior.
   - Extend simple-adp-suite to list the new providers/tasks, dry-run a deterministic plan, run/resume the suite, and report results. Keep simple-adp-benchmark working as a compatibility entry point for the existing OpenML benchmark.
5. Integrate documentation and reproducible operation.
   - Document the dataset manifest fields and access filter, data cache location, each task’s row/window construction, split policy, target encoding, loss, metric, and known exclusions.
   - Document how to register a future provider or task adapter without modifying the central scheduler or model algorithms.
   - Provide one canonical launch command that selects the complete enabled catalog and all model routes. Keep --task-limit, --fold-limit, provider/suite selection, dry-run, resume, and output directory controls available.
   - Do not launch the benchmark while implementing. The explicit smoke profile runs one epoch with batch size equal to the training partition, never including validation or test rows. Full benchmark runs remain separately launched and use configured batch-size/resource settings.

- Unit-test each task’s input construction, labels, output shapes, loss, validation-score direction, prediction conversion, and metrics using deterministic fixtures.
- Test chronological target boundaries, subject/record/user isolation, ranking group integrity, deterministic negative sampling, unknown user/item categories, anomaly class weighting, and validation-only threshold selection.
- Test provider catalog eligibility/provenance, stable split hashes, manifest compatibility checks, resume behavior, and task-aware report ranking.

## Assumptions and fixed limits

- The catalog is exhaustive over the named curated sources and their eligible entries, not over every dataset published worldwide.
- Sequence prediction means both future-value prediction and per-step sequence labeling. Whole-series UCR/UEA classification is not added as a separate task because it duplicates the requested label-prediction functionality without a per-step target.
- Strict novelty detection is out of scope; anomaly detection uses labeled anomalies during training.
- Search ranking is implemented as a reusable grouped-ranking task and benchmarked via per-user item ranking. Web-search query–document benchmarking is omitted under the no-agreement rule; CTR is omitted for the same access constraint.
- The standard suite is CPU/GPU configurable through the existing runner. The smoke profile’s full-training-partition batch is not a claim that the full dataset should be loaded as one batch for full-scale experiments.

## Engineering sequence and exact module boundaries

Implement in dependency order so every stage has a runnable contract before the next one is connected.

1. **Task contract (`src/simple_adp/tasks.py`).** Preserve the existing three-argument task calls when context is absent. Add `fit_targets_with_context`, optional `context` to loss/validation/metric hooks, `output_spec`, `batch_group_key`, `primary_metric`, and metric directions. Context is row-aligned metadata, not an input to the MLP unless a provider deliberately includes its corresponding values in `X`. This keeps query, timestamp, event, and entity metadata out of model features by default.
2. **Task algorithms (`advanced_tasks.py`).** Implement each task as an adapter. Forecasting reuses regression MSE and emits one output per requested horizon. Sequence labeling emits a contiguous `(steps * classes)` vector, reshapes it to `(batch, steps, classes)`, applies cross-entropy to flattened positions, and reshapes predictions back. Event classification reuses class-index cross-entropy and adds event aggregation only when event IDs are supplied. Ranking emits one score, groups rows by integer `group_id`, skips groups lacking either class, selects negative index `positive_ordinal % negative_count`, averages pairwise `softplus(s_negative-s_positive)` within each usable group, then averages groups. Anomaly/preference tasks emit one logit and use `binary_cross_entropy_with_logits(pos_weight=N_train_negative/N_train_positive)`; only validation labels may select the classification threshold.
3. **Framing (`task_preparation.py`).** Convert each entity to chronological source-row positions first. Forecast examples use exactly the preceding 128 observations, flatten time-major/channel-minor, and target observation `start + lookback + horizon - 1`; use stride 1 below 10,000 observations and 24 otherwise. Return target source positions so the split can be built on target time; allow validation/test feature windows to read earlier history. Sequence examples use full, non-overlapping 128-row blocks and drop only incomplete tails. Event window labels are positive on interval overlap (inclusive endpoints). Grouped splits sort each user's rows stably by timestamp and assign the first floor(80%), next floor(10%), and remainder to train/validation/test. Anomaly splits use seeded shuffling per class, allocate floor of 60/20/20, and distribute rounding remainders deterministically; reject any class too small to populate all partitions.
4. **Provider contract (`runner/datasets.py`).** Keep `DatasetTaskRef` stable and JSON-serializable. Providers must return already framed `X`, `y`, context, an ordered feature schema, task adapter, task family/variant, split protocol, provenance and a source-content SHA-256. They must be deterministic when given the same artifact version. Store downloads below `SIMPLE_ADP_DATA_CACHE` or `~/.cache/simple-adp/datasets`; never store source payloads in Git. Split arrays must be disjoint, non-empty, checksummed, and reloaded from the persisted archive by workers.
5. **Provider implementations (`runner/public_datasets.py`, `runner/temporal_datasets.py`, `runner/sequence_datasets.py`, and source-specific modules).** Parse each source in its own loader; do not put format parsing into `SuitePlan` or model adapters. For MovieLens, parse `u.data` using tab columns and `ratings.dat` using the literal `::` separator; retain user/item IDs as categorical strings, ratings as float targets, timestamps as int64 context, and stable integer user codes as `group_id`. Register three references per version (`rating`, `preference`, `ranking`), each using the same user-chronological split. For Electricity, parse the UCI semicolon table with decimal commas, frame all meter channels into 128-lag rows, choose stride 1 when the source has fewer than 10,000 observations and 24 otherwise, and include the chosen stride in the content signature; split by target source-row position. For HAPT, pair each raw accelerometer and gyroscope file by experiment/user, apply the source interval labels to one-based inclusive sample ranges, retain only fully labeled non-overlapping 128-row blocks and their zero-based source start positions, and split by source subject IDs; select the highest sorted `ceil(20%)` validation subject IDs only from the official source train IDs, leaving the other train IDs for training and official test IDs for testing. Sequence boundaries are one-based transition positions in source coordinates; count the boundary between consecutive windows only if they share subject/experiment and `next_start == prior_start + 128`, and never bridge a dropped or unlabeled window. For Monash, pin the Australian Electricity Demand Zenodo record/version, parse its TSF metadata and five state series, emit half-hour horizons 1, 7, and 28, use 128 lags and stride 24 for each long series, and split target positions chronologically per series. Record the CC BY 4.0 license, citation, and artifact digest. For NAB, pin the repository commit, parse `combined_labels.json`, make 128-value windows at stride 24, assign a window label on any inclusive interval overlap, retain source-file ID and event ID only as context, and stratify whole files by whether each contains an anomalous window. Use `settings.seed` when provided, otherwise seed 42; for each class sort file IDs lexically, shuffle with a local NumPy `default_rng(seed)`, assign floor 60/20/20 counts, and distribute leftover files in train/validation/test order. Reject the split if any partition is empty or lacks either window class. Record the archive SHA-256 and per-file upstream attribution; do not imply repository-code licensing grants rights to payloads. MIT-BIH and LTDB use PhysioNet Open Access WFDB files, resample signals to 360 Hz, map beat symbols to AAMI classes, keep 201/202 together, and ensure all observed classes occur in training. For ODDS, implement an explicit 24-artifact allowlist: cardio, thyroid, satimage-2, lympho, glass, vowels, musk, letter, speech, satellite, shuttle, breastw, arrhythmia, ionosphere, mnist, optdigits, http, smtp, mammography, annthyroid, pendigits, ecoli, wine, and vertebral. For each, validate `X`/`y`, row alignment, exact feature width, finite numeric features, binary label set `{0,1}`, documented transformation, direct artifact endpoint, original source, and source/artifact terms independently. Use each artifact's individually documented binary mapping and seeded stratified 60/20/20 split. Do not claim that the original source license automatically covers the ODDS-derived MAT file or redistribute the MAT payload. Keep WBC, ForestCover, Pima, Mulcross, Yeast, Heart, and Seismic disabled with the per-artifact availability/transformation reasons in the catalog; recheck those reasons before enabling them.
6. **Training and resume (`training.py`, `search.py`, `estimator.py`).** Slice context with exactly the same positional indices as `X` and `y`. For ordinary tasks keep the current random minibatch path byte-for-byte in behavior. For grouped ranking, shuffle group IDs once per epoch with the existing seeded CPU generator; pack whole groups until adding the next group would exceed the configured batch size; never split a group. Persist the complete epoch batch plan and cursor for exact interrupted-stage resume. Keep current architecture, best architecture, optimizer reset at architecture boundaries, and checkpoint signatures unchanged except that the task/context signature must now include stable metadata used by training.
7. **Model adapter (`runner/models.py`).** Resolve `data.task_adapter` first and use the legacy classification/regression fallback only if it is absent. Split context with the same positional row selector. Fit the estimator on training rows and explicit validation rows, evaluate validation task metrics, optionally select threshold from validation only, then evaluate test exactly once. Return task family, variant, split protocol, primary metric, metric directions, and test metrics; never pass test context into fitting or selection.
8. **Plan and worker (`runner/plan.py`, `runner/worker.py`).** Expand a provider suite into stable refs, fetch metadata and splits once while building the plan, serialize source/version/license/checksum/schema/task metadata into each ref, and hash the provider suite, route matrix, task refs, data content hashes and split hashes into the compatibility signature. Workers reconstruct the provider from the ref, verify the reloaded dataset ID, source-content hash, row/feature counts, schema, task identity, context fields and provenance against the planned metadata, verify the persisted split, and run the same adapter. Keep provider errors explicit and terminal; do not silently drop an unavailable dataset or route.
9. **Reports (`benchmark_report.py`, `runner/scheduler.py`).** Flatten only declared adapter metrics. Rank route results within `(provider, suite, task, dataset, task_family, task_variant, metric)` using that metric's declared min/max direction. Compute macro dataset means only within the same task family/variant. Keep validation selection scores separate from outer-test metrics. Keep the hardness screen report-only for new tasks unless its gate is explicitly given a meaningful task-specific rule; do not apply accuracy/R-squared ceilings to ranking or event metrics.
10. **CLI and default catalog (`runner/plugins.py`, `runner/launcher.py`).** Register providers explicitly and expose their suite names through `--list-suites`. Preserve existing default OpenML selections. Publish a separate explicit complete-catalog command that names every enabled provider suite; do not make a potentially very large, network-dependent catalog an implicit default. Dry-run must build the full route/task/split matrix without scheduling workers. `--smoke` must set one epoch and `batch_size=len(train_indices)` in each worker, where `train_indices` excludes validation/test; no downloaded dataset or cache is required by unit tests.
11. **Acceptance order.** First run adapter/framing unit tests and local fixture provider tests. Then run existing estimator/search/checkpoint tests unchanged, runner plan/worker/report tests, route-matrix dry-run tests, and one CPU integration smoke per task family using local synthetic fixtures. Finally run the complete test suite and inspect the dry-run manifest for all enabled routes and sources. Do not launch the full experiment matrix during implementation.

## Execution blueprint: exact deliverables, design decisions, and gates

This section turns the contracts above into an ordered implementation checklist. A phase is complete only when its named artifacts and tests exist and its gate passes. Do not mark a source enabled based on a catalog entry alone.

### Phase A — Freeze contracts before adding providers

1. Read the existing task, estimator, training, checkpoint, runner data, plan, worker, report, and CLI interfaces. Record compatibility-sensitive call signatures and serialized field names before editing.
2. Add optional context and task metadata additively. Missing context must follow the pre-extension code path, including the existing sampler and loss call sequence. Do not change default classification/regression output shapes or metric names.
3. Define one serialization-safe task specification: task family, variant, output shape/classes, loss identifier and parameters, primary validation metric, metric direction, prediction conversion identifier, and any context keys consumed by the adapter. Store values, not Python closures, in manifests.
4. Define `PreparedTaskData` invariants and validate at construction/load boundaries: row counts agree across X/y/context; feature schema length equals input width; context keys are stable strings and each value has one entry per row; numeric model inputs are finite after the documented preprocessing path; split indices are unique, in-range, disjoint, and collectively cover the intended rows.
5. Gate A: existing task adapter, estimator, checkpoint, and runner unit tests pass unchanged; new contract tests prove calls with omitted context behave as before and reject misaligned context.

### Phase B — Implement task mathematics independently of datasets

1. Implement one adapter per behavior in `advanced_tasks.py`; keep source-specific encodings out of these classes.
2. Forecasting: use the regression output/loss contract; target width equals the declared horizon count. Prediction conversion returns `(rows, horizons)` and validation minimizes MSE unless the caller explicitly selects another regression metric.
3. Sequence labeling: declare `steps` and class count before model construction; model output width is `steps * classes`; reshape logits to `(batch, steps, classes)`; flatten labels only for cross-entropy; restore `(batch, steps)` class predictions. Reject labels outside the declared class mapping.
4. Event classification: train on window labels with classification loss. Compute ordinary window metrics always. Compute event metrics only when event/series context exists; build contiguous predicted alarm intervals per series and use deterministic one-to-one matching so one true event cannot match multiple alarms and precision/recall remain in `[0,1]`.
5. Grouped ranking: require a scalar score and integer group IDs; for each group, enumerate positive rows in original stable order and choose negative `positive_ordinal % negative_count`; compute `softplus(negative_score - positive_score)` for each pair, average within each usable group, then average usable groups equally. Skip groups missing a positive or negative. Validation score is this same pairwise objective, minimized; NDCG@10 is a separately reported metric, not the optimization score.
6. Binary preference and supervised anomaly: emit one logit; calculate `pos_weight` from training labels only; use logits BCE. Threshold selection may inspect validation labels only, uses a documented deterministic tie-break, and is frozen before test evaluation. Rating prediction remains regression and is not thresholded.
7. Gate B: fixture tests assert exact tensor shapes, hand-calculated loss values, validation direction, deterministic pair selection, metric bounds, threshold isolation, and behavior on empty/degenerate groups.

### Phase C — Implement deterministic framing and split primitives

1. Make framing functions pure: arrays and explicit parameters in, prepared arrays/context/source positions out; no downloads, global RNG, or hidden cache access inside these functions.
2. For forecasting, order rows within each entity by timestamp/source position, construct each 128-step history from preceding observations, flatten in time-major then channel-minor order, and label each example by target source position. Split by target positions at 70/10/20 chronological boundaries; permit earlier-partition history as features, but never target leakage across boundaries.
3. For per-step labeling, form contiguous non-overlapping blocks of 128, drop incomplete tails, and keep only blocks whose 128 labels all map to known classes. Persist block start/end positions and entity IDs in context.
4. For interval events, use inclusive overlap: `[window_start, window_end]` intersects `[event_start, event_end]` iff `window_start <= event_end and event_start <= window_end`. Preserve source event IDs in context and assign a stable alarm ID after thresholding contiguous positive windows within a series.
5. For grouped data, sort rows by `(entity_id, timestamp, original_row_index)`; calculate train/validation cutoffs per entity using floor 0.8 then floor 0.1, with the remainder assigned to test. Keep every entity’s rows in one chronological order and ensure all rows occur in exactly one partition.
6. For seeded stratification, use a local RNG instance initialized from the run seed; split each class independently; allocate floor counts and distribute remainder in fixed partition order train, validation, test; fail with a message naming the class if any required split would be empty.
7. Gate C: exact expected windows, flatten order, inclusive boundary cases, split membership, determinism under repeated calls, and no-overlap/coverage properties pass on small hand-constructed fixtures.

### Phase D — Add and audit source loaders one source at a time

1. Each provider owns artifact URL/version, cache filename, parser, source metadata, task refs, deterministic split, and fixture loader. Reuse only generic cache/hash/split helpers; never put parsing or source policy into the scheduler.
2. Download to a temporary sibling file; verify successful completion and parse before atomic replacement. A failed request/parser must leave no partial cache file. Offline mode must fail with the expected cache path and must not access the network.
3. Hash the exact cached source bytes with SHA-256. Keep source content digest distinct from split-index digest. Serialize dataset name/ID, provider/task IDs, source/artifact URLs, versions, transformations, attribution/license terms, schema, row/feature counts, and split policy into plan metadata.
4. Apply the same direct-access eligibility test per artifact: test its actual download endpoint without credentials, account, approval, or agreement; inspect original-source terms and derived-artifact terms separately; record uncertainty precisely; do not infer a license from the host, collection, or source code. Do not redistribute cached payloads.
5. Build a fixture for every parser using a locally generated minimal archive or injected byte/array reader. Assert source columns, transformation, labels, order, feature count, context, digest behavior, and deterministic split. Include malformed/truncated/wrong-schema cases and assert explicit errors.
6. Gate D: every enabled task ref loads offline from a fixture, carries complete provenance, and creates non-empty disjoint splits; every disabled/ineligible artifact has an explicit catalog reason.

### Phase E — Preserve runner identity, routing, and replay behavior

1. Keep model-route enumeration independent of task family. For each task, route exactly the registered 14 canonical ADP IDs, two generic profiles only where applicable, fixed MLP grid as configured, and the 50 standalone vanilla routes. Assert the route multiset is identical across all task families.
2. During planning, materialize metadata and split indices once, persist them, and include their hashes plus task adapter specification and route settings in the compatibility signature. A changed artifact, schema, split, task output, or route matrix must invalidate resume with a clear signature mismatch.
3. At worker start, reload through the registered provider, compare planned and loaded identity/hash/shape/schema/task/context/provenance fields, then verify split hashes before creating a model. Treat mismatch as terminal; never silently substitute or omit data.
4. Slice context using the same row index tensor as X and y. Grouped batches are whole groups; deterministic group order and complete batch plan/cursor are checkpointed. Ordinary-task minibatch RNG behavior stays unchanged.
5. Reset optimizer/scheduler only at documented architecture-stage boundaries. Mid-stage resume restores model, optimizer, scheduler, RNG, stage/candidate position, counters, and ranking batch plan/cursor. Test both boundary reset and interrupted-stage continuation.
6. Gate E: fixture-backed full SuitePlan builds every route, workers reject intentionally mutated metadata/splits, and an interrupted grouped stage resumes with the exact next batch and deterministic result.

### Phase F — Metrics, screening, CLI, and operator documentation

1. Each adapter declares metric names and directions. Result flattening accepts only those declarations; report grouping keys include provider, suite, dataset, task family, task variant, and metric. Never combine values with different units or direction.
2. Keep test metrics read-only and post-fit. Validation metrics alone drive architecture selection and thresholds. The existing hardness screen remains restricted to the existing supported classification/regression rule until a separate task-specific screen rule is specified and tested.
3. Register providers explicitly. `--list-suites` must work even when an optional parser dependency is absent and must tell the operator which extra enables it. Explicit full-catalog commands must list all enabled suites; default commands remain unchanged.
4. Dry-run must persist the complete task/split/route manifest without starting workers. Smoke mode means exactly one epoch, and each job’s batch size equals its count of training rows only. Do not execute the full matrix during implementation.
5. Update README and catalog together: launch command, optional extras, cache, artifact terms, source transformations, split details, supported task semantics, and exclusions must agree with provider metadata and tests.
6. Gate F: list-suites, dry-run manifest inspection, `git diff --check`, generated source-function-map check, focused tests, then full test suite. Report static checks, tests, smoke experiments, and real data training as distinct evidence categories.

### ODDS inventory decision record

The ODDS multidimensional point-data index contains 31 entries. This implementation enables 24 individually inventoried entries and leaves seven explicit exclusions. Before changing the allowlist, inspect the official ODDS entry for every candidate and record the artifact endpoint, transformation, feature count, original source, source terms, and whether the artifact can be fetched directly without an account or agreement. Never extrapolate one artifact's source or license metadata to another. The reviewed candidate set and explicit exclusions belong in `docs/SUPERVISED_DATASET_CATALOG.json`; the registry must be generated from or tested against that catalog so they cannot drift.

The current source review found 24 entries with direct public MAT artifacts: cardio, thyroid, satimage-2, lympho, glass, vowels, musk, letter, speech, satellite, shuttle, breastw, arrhythmia, ionosphere, mnist, optdigits, http, smtp, mammography, annthyroid, pendigits, ecoli, wine, and vertebral. Candidate activation remains conditional on verified dimensions, `X`/`y` shape and label mapping, artifact page/transformation metadata, artifact-specific terms, fixture tests, and worker-plan compatibility. The HTTP MAT was downloaded and read as HDF5: its actual shape is `(3, 567498)` with 2,211 positive labels, so the loader transposes it to 567,498 rows by 3 features. This differs from the ODDS detail prose (567,497 rows) and index table (567,479); record the discrepancy and use the acquired artifact's actual shape as its integrity contract.
